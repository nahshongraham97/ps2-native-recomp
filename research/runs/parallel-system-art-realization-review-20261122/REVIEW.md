## P2: movie host-capacity rejection moved before collection/error precedence

movie_gl_device.cpp:275 in the committed candidate checks width/height>INT_MAX in validate_image_upload before collect_video and incoming GL error at277/278. Old upload_rgba validated the movie frame first, then collected, checked incoming GL error, queried host limit and only then rejected INT_MAX dimensions. New upload_rgba still calls unchanged validate_movie_upload, which accepts representable dimensions above INT_MAX when a legitimate matching host span is supplied (e.g.width0x80000000,height1 with8GiB resident/reserved backing). The new shared helper returns host_capacity immediately, skipping collection and changing fence/incoming-error precedence. Overflow is a different case: unchanged validate_movie_upload already returns invalid_frame before this helper, so this finding does not assert a new movie overflow regression. Restore the old movie ordering while retaining safe arithmetic/GLsizei checks before actual allocation/submission. No GPU execution of an enormous span is needed to prove the control-flow difference; a headless call-order check can verify the boundary.

## Deletion failure recovery bound

revoke_image marks the capability revoked before deletion, which correctly prevents subsequent name access/sampler use. Successful deletion zeros the name and repeated revoke is idempotent. Retained image leases use weak Session authority; wrong thread/context, drain and retired Session checks precede object access. Immediate deletion does not require resurrecting a deleted binding. No ordinary successful-delete-plus-spurious-error scenario was demonstrated: n=1 is valid, and normal GL error-generating commands have no state effect. Do not assert this generic hypothetical as an observed bug.

However image_error discards the actual error code and all post-delete failures retain a numeric name for retry while admission remains open. The Khronos error contract makes GL state undefined after OUT_OF_MEMORY, so that case does not prove the name still denotes this image; generic retained-name recovery is not established for every error class. A fatal/quarantined Session or an error-specific proven policy is needed before claiming universal recoverable deletion. This is an unexecuted error-policy limitation, distinct from the proved movie ordering defect. Validation05 tests successful/idempotent revoke, not injected delete failure or ambiguous name reuse. Existing retirement deletion predates this candidate; this review does not relabel all inherited behavior as newly authored.
